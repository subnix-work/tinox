# Message translation (`tr`, `trc`, `trn`) and string extraction

Text that users see is marked in the source and looked up in a **GNU gettext catalog** at run time, so translators
work with the standard tools (`msginit`, `msgmerge`, `msgfmt`, Poedit, Weblate, ...). No library import is needed:
`tr`, `trc` and `trn` are built in (#588).

```tinox
class Main
{
    fnc main() -> Int32
    {
        println(tr("Hello"))                                       // plain text
        println(trc("menu", "Open"))                               // same word, different meaning: a context
        println(trn("%1 file", "%1 files", 3).argInt(3))           // plural: singular, plural, count
        println(tr("Saved %1 files to %2").argInt(3).arg("disk"))  // placeholders
        return 0
    }
}
```

* `tr(text)`, `trc(context, text)`, `trn(singular, plural, n)` return the translation, or the English source text when
  there is none (for `trn` with the English rule: singular for `n == 1`).
* **Placeholders instead of concatenation.** `%1`..`%99` in the text are filled with `.arg(String)` or
  `.argInt(Int64)`; each call replaces the lowest-numbered placeholder that is still present. A translation may
  reorder them (`"Auf %2 wurden %1 Dateien gespeichert"`). Never build a translatable sentence by `+`.
* **Texts must be string literals.** The compiler rejects `tr(name)` and `tr("a" + b)` ("needs string literals"),
  because only literals can be extracted. A class that defines its own static `tr`/`trc`/`trn` keeps calling its own.

## Catalogs at run time

| | |
|---|---|
| Language | `LANGUAGE` (colon separated list, first with a catalog wins), else `LC_ALL`, `LC_MESSAGES`, `LANG`. Encoding and `@modifier` are ignored; `de_DE` also tries `de`. `C`, `POSIX` or unset: no translation. |
| Catalog file | `<dir>/<language>/LC_MESSAGES/<domain>.mo` |
| Directories | `TINOX_LOCALE_DIR`, then `locale/` next to the executable, `./locale`, `/usr/share/locale` |
| Domain | `TINOX_TEXTDOMAIN`, default `messages` |
| Plural rule | the `Plural-Forms:` header of the catalog (any gettext expression: `n != 1`, the three-form Slavic rules, ...) |

The catalog is read once per process. One language is used (the first candidate with a catalog); merging several
catalogs is not done. Untranslated and `fuzzy` entries are not in the `.mo` (msgfmt drops them) and fall back to the
source text.

## Extraction

```sh
tinox i18n extract                       # src/ of the project -> messages.pot
tinox i18n extract --out po/app.pot src  # other output / paths
tinox i18n extract --out - Main.tnx      # stdout
msginit -l de -i messages.pot -o de.po   # or: msgmerge --update de.po messages.pot
msgfmt de.po -o locale/de/LC_MESSAGES/messages.mo
```

`extract` scans the token stream of every `.tnx` file (so it also finds calls in files the program does not
import yet), merges identical texts with all their `#: file:line` references, and writes `msgctxt`, `msgid`,
`msgid_plural`. Output is deterministic. A call whose texts are not plain literals is reported with its position
and the command fails. `Foo::tr(...)` and `x.tr(...)` are not the built-in and are skipped.

Verified with `msgfmt` (compiling the catalogs the program loads) and `msgmerge` (accepting the extracted template and
matching every entry of a translator's `.po`) in `crates/tinox/tests/i18n.rs`.

## Limits

* Catalog lookup is by exact text; there is no `ngettext`-style per-domain switching (`dgettext`) and no runtime
  language change API: the language is read from the environment on first use.
* The Qt/KDE bridge case from the issue (strings crossing into `KLocalizedString`) still needs the IDE side to call
  `tr` before handing the text over; extraction here only sees Tinox sources.
